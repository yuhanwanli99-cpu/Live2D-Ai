## 1. 结论

现行程序证明的是一条 Live2D × AI 底座：纯对话、整句 TTS、按音频时钟对口型、皮套渲染。
桌宠不在这条链上。`pet-desktop` 与原生窗口壳已于 2026-10-01 移出构建，crate 只留在
tag `checkpoint/pre-d1-dormant`。

嘴型和 TTS 已经在底座里。表演（表情、头、身体）还在底座旁边：协议写得细，运行时有多条写入者，
core 的动作采样器没有驱动方。把「代码已经是完整底座」说满，会把这条缝盖住。

文档把三套产品叠在同一仓库里：2026-09-11 的说话与口型底座、2026-09-21 的「酒馆内核 + 导演属本体」、
研究文档里的桌宠清单。第三套和代码方向相反。这是第一笔负债。文档行数多，是这三套口径没分开的结果。

## 2. 已经闭环的底座

关掉可选 Mod 之后仍能独立转完的链路：

```text
文本 → LLM（OpenAI 兼容，请求体无 tools）
    → 引擎按句读切句
    → TTS 整句合成
    → WebSocket PCM（句首/句尾由引擎给出）
    → 前端 WAV + <audio>
    → 服务端音量包络按 currentTime 写 ParamMouthOpenY
    → /render 的 wasm 皮套
```

| 层 | 主人 | 守住的事实 |
| --- | --- | --- |
| 回合 | `live2d-ai-core` reducer | epoch、生成闩锁、播放闩锁 |
| 说话 | `live2d-ai-runtime` `ConversationEngine` | 一句一个 TTS 任务；思考不进 TTS；失败轮 `text_fallback` |
| 出声 | `live2d-ai.toml` 的 `[tts]` | 端点只来自配置。`local-tts-melo` 只拉起进程 |
| 嘴 | `crates/l2d-wasm-demo/src/mouth.rs` | 线性 RMS → dBFS → `ParamMouthOpenY`；非有限值回 0；原生可测 |
| 姿态 | `crates/l2d/src/pose_stack.rs` | `base < idle < input < physics < final_override`，每帧重合成 |
| 壳 | Flutter `/app/` | 唯一界面。默认入口是 `--web` |

注册表 6 个：`external-input`、`persona`、`voice-input`、`memory`、`director`、`local-tts-melo`。
没有桌宠，没有壁纸。缺省启用的是外部分发注入和 Melo 拉起。

这几处是皮套接入最容易假绿、而这里做成了可回归的部分：句界由引擎给出；口型参数被预设测试排除；
静音不改口型；错误码在日志和 WebSocket 里是同一个字符串；Mod 失败只关掉自己。

`mouth.rs` 的分贝映射和 `pose_stack.rs` 的五层栈是底座级实现。它们现在就在产品路径上。

## 3. 表演还没有进这条底座

表演协议 v1（`docs/architecture/performance-protocol-v1.md`）把「说什么」和「怎么演」拆开：
`segments` 只切分原文，`body` / `head` / `expression` 写归一化轴，不写 `ParamXxx`，时间锚在音频时钟。
这个形状是对的。它还不是已经证明完的那一层。

协议头注写明：2026-09-26 那一波是另一工作树上的文档冻结。说话权归属（Q1）协议自己标成未裁决。
运行时同时有这些写入者：

| 路径 | 实际做什么 | 和表演的关系 |
| --- | --- | --- |
| `live2d-ai-core` 的 `action/`、`performance/` | 仍编译，不变量 4 和 6 以它们为前提 | 无驱动方。`action_tx` 固定不投递 |
| `[performance]` | 默认关的第二路 LLM，出 segments + cues | 可选的整轮表演 |
| `director` | 缺省停用的 Mod；启用后按**用户输入**发 `action_cue` | 现行会让皮套动的旁路 |
| `SentenceCleaner`（`cleaning.rs`） | 同一 `[llm]` 端点、关思考，一句换成 `display` / `speech` | 决定哪几个字上屏、哪几个字送 TTS。不产 body/head/expression |
| `clean_for_tts` | 纯函数，只拆标记 | 不是第二模型 |

`SentenceCleaner` 不该并进「三条第二表演 LLM」。它和 cue 是两件工作。cue 的重叠是
`[performance]` 与 `director`。规则层打分的是用户刚说的话；角色回复只在问号上补一次歪头和思考脸。
2026-09-21 的裁决又把导演说成产品本体。代码把它放在缺省停用的 Mod 里，`main.rs` 头注仍写「零投递」。

导演关掉之后口型仍应跟着 TTS 走：预设表禁止写 `ParamMouthOpenY`，这是测试钉住的结构。
本轮没有在活服务上开关导演再听一遍。

「通用皮套」目前证明到白模型这一张。缺参数会丢弃这条 cue，不会按新皮套重映射。

## 5. 对照稿：采纳什么，不采纳什么

采纳：

- 初评把本仓库当成桌宠，是误读。底座口径才贴代码。
- 第一笔负债是三套产品口径叠在一起。行数、注释编年史是表现。
- `mouth.rs` 与 `pose_stack.rs` 是底座级实现。
- Mod 隔离、棘轮门禁、loopback、密钥不回显，是真做过事故才有的结构。
- 公开 git 历史被压成单根之后，协议兼容矩阵只活在散文和 tag 说明里。

不采纳：

- 「表演协议 v1 是已经做成的最强底座资产。」形状对，主人没定，默认路径不经过它。
- 「三条第二 LLM 收成一条」把 `SentenceCleaner` 算进表演。清洗管台词切片，不管肢体。
- 「crates 平级所以没分层。」workspace 里 Mod 与 `l2d` 并列是正常的。模糊的是文档地图，以及导演既被写成产品本体、又缺省停用。`pet-desktop` 已经不在 `crates/` 里。
- 「再做一个宿主才算底座。」仓库红线是不得再引入第二个 UI 壳。缺的是一份别人能对照跑的向量，不是第二扇窗口。
- 「主要负债不在代码。」口型这条链的代码站得住；表演多写入者是代码负债，不只是措辞。
- 并行稿 §6 的「代码已是底座」和 §2「表演还没进底座」互相盖住。本文取 §2。

并行稿 §7 写明没跑测试、没复现开关导演。那些限制继续有效。其 `code-stats` 数字（docs 42,556 / 45,000，`>500` 44/44）是它的测量，本轮未重跑。
