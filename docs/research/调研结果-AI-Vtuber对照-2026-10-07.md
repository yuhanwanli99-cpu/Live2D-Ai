## 0. 给导演讨论的结论

1. **对方没有导演层。** 它的主循环是「直播事件 → 过滤/短路 → 一段要念的文本 → TTS → 把音频 URL 交给外部虚拟身体」。表情、头、身体参数不在这条链上。
2. **仓库自带的 Live2D 页不驱动皮套表演。** `live2d.enable` 只起一个静态 HTTP 服务，页面是 CyberWaifu 式样例（摸头说话、按时段问候）。真正「有张脸」时，音频被 POST 给 Unity / EasyAIVtuber / 数字人播放器 / 另一个 Live2D 项目。
3. **能进本次导演讨论的只有三件事，而且都不该写进 `derive()`：** 事件种类（弹幕 / 礼物 / 入场 / 关注 / 闲时）、按种类插队且低优先级挤不掉已在队列里的高优先级、短窗口内把同一类事件收成最后几条。这三件属于「谁有资格变成一轮 `TurnPrompt`」，导演仍只读那一轮的用户侧文本。
4. **明确留在对方仓库的：** 平台协议与逆向脚本、助播去回应角色自己的回复、关键词表直接变串口/图片/文案、把身体外包、示例模型 Hiyori、整仓 Python 单体。

## 2. 对方的「表演」实际走哪条路

```text
平台线程 / 本地麦克风 / 定时器
        │  统一成 {platform, username, content, type}
        ▼
My_handle.process_data          短窗口攒批（forget_duration + reserve_num）
        ▼
comment / gift / entrance / follow / talk / idle / schedule
        │  违禁、黑名单、去重、关键词短路、本地问答、点歌、画图
        ▼
llm_handle 或固定文案          产出「要念的一整段文本」
        ▼
audio_synthesis_handle
        │  data_priority_insert 按 type 插进 message_queue
        ▼
visual_body 分支
        ├─ xuniren / EasyAIVtuber / digital_human_video_player
        │    / live2d-TTS-LLM-GPT-SoVITS-Vtuber   → POST 音频路径
        └─ 其他                                   → 本机播放器
```

证据：

- 事件分发：`utils/my_handle.py` `process_data` / `process_last_data`（约 4116–4177 行）。`comment_handle` 从约 2976 行起。
- 优先级队列：`utils/audio.py` `data_priority_insert`（548–621 行）。数值在 `config.json` → `filter.priority_mapping`。
- 身体切换：`utils/audio.py` 1425–1434 行。`live2d_TTS_LLM_GPT_SoVITS_Vtuber_api`（511–528 行）只 POST `{"action":"talk","data":{"audio_path":...}}`。
- 自带 Live2D：`main.py` `web_server_thread`（52–59 行）是 `http.server`；`live2d.enable` 为真才在 `main.py` 140–144 行拉起。`Live2D/README.md` 写明改 `bundle.js` 里的 `e.ModelDir = ["Hiyori"]`。`Live2D/js/message.js` 只有摸头/摸身体的气泡和 30 分钟一次的时段问候，没有 Cubism 参数、没有口型、没有动作消息。

`bert_vits2.emotion`、`gpt_sovits.webtts.emotion` 是 **TTS 引擎的情绪字符串**（例如「Happy」「正常」），写在合成请求里。它们不驱动 Live2D 参数。

## 4. 可借鉴的部分（按该放进哪一层）

### 4.1 值得放进这次导演讨论的：准入，不是表演

导演今天只看见「这一轮的正文」。直播把弹幕、礼物、入场、关注都收成同一个 `say` 之后，导演无法区分「有人刷了礼物」和「有人说了句话」，也挡不住一秒钟几十条弹幕各开一轮、各发一条 cue。

对方把这件事做在说话队列上，数值是配置不是代码：

| 优先级（越大越先） | `filter.priority_mapping` 里的 type |
| --- | --- |
| 999 | `reread_top_priority`（打断式复读） |
| 30 | `talk`（本地语音）、`reread` |
| 25 | 助播文本 / 助播音频 |
| 20 | 弹幕、念弹幕、礼物、入场、关注、点歌、本地问答音频、按键映射、积分 |
| 10 | 闲时、定时、动态文案、图像识别定时 |
| 1 | 循环文案、异常报警 |

插入规则（`audio.py` 586–612 行）：从队尾往前找，插到「最后一条优先级 ≥ 新条目」的后面，同级保持先来后到。算出来的下标已经 ≥ `message_queue_max_len`（默认 50）就**丢掉新来的**，不挤掉队里已有的高优先级。队列满时，闲时和文案进不去，礼物和弹幕还在。

本仓对应点是 `external-input` 的 `busy`：pending 满了整条丢掉，不看来源。若导演要在直播里用，讨论的是给 `TurnPrompt` 加一个**来源标签**（弹幕 / 礼物 / 入场 / 本地聊天），并在进主链之前做上面这种准入。标签到了导演，规则层可以让礼物走更明确的表情、弹幕仍走现在的词表。`derive()` 本身继续是纯函数，不持有队列。

同一类事件的短窗口收束在 `process_data`（4116–4130 行）和 `get_interval`（4179–4193 行）。默认：弹幕 1.0 秒只留最后 1 条，礼物 5 秒留 1 条，入场 5 秒留 2 条，到点才逐条处理。另有 `is_data_repeat_in_limited_time` 做限时去重。这能直接减少导演被弹幕洪水触发的次数，适合放在 sidecar 或 `external-input`，不必进 cue 仲裁器。

### 4.2 可以记下来、不要写进导演

**闲时开口的门闩。** `main.py` `idle_time_task`（1162–1570 行）有三种触发：房间无新消息超过随机的 `idle_time_min..max`（默认 30–60 秒）；待合成队列短于阈值；待播放队列短于阈值。播放积压超过 `wait_play_audio_num_threshold`（默认 10）时，把闲时计数打回 `idle_time_reduce_to`（默认 0），等于重新等满一个周期（`main.py` 272–283 行）。内容三选一，默认只开了本地 wav：固定文案、拿文案当用户消息去问 LLM、播本地音频，三种轮着来，播完从列表里弹出，空了再洗牌。

这是「直播间冷场要有人说话」，不是皮套情绪。本仓闲时生命体征已经覆盖「没人说话时身体还活着」。若以后要冷场说话，门闩（队列短才触发、积压时把计时打回去）可以照这个行为做；开口的文本仍走主模型，导演只对那一轮用户侧文本（这里的「用户」是闲时任务自己塞进去的提示）给 cue。不要把 wav 列表和文案轮播做进 director。

**命中表短路，放在 LLM 之前。** `comment_handle` 的顺序是：限时去重 → 黑名单 → 积分命令 → 违禁与纯符号 → 关键词表 / 自定义命令（命中则本条不再进 LLM）→ 可选「念弹幕」→ 本地问答 → 点歌 → 画图 → 翻译 / 搜索 → LLM。关键词表（`key_mapping`，`my_handle.py` 2459 行起）的一条配置同时带 keywords、礼物名、热键、文案、本地音频、串口字节、图片路径。命中后播的是文案或 wav，不是 Live2D 动作。

对本仓：本地问答、点歌、画图都是另一条产品，不在导演范围。若要「这句话不用问模型」，短路应在主链 `say` 之前，导演仍能看到最终被采纳的那句用户文本。串口和换图不要进导演。

**括号随机与变量替换**（`common.py` `brackets_text_randomize`、`dynamic_variable_replacement`）：文案里写 `[甲|乙]` 随机抽一个，`{username}` `{gift_name}` `{time}` 替换。本仓 `external-input` 已有 `text_template` 的 `{text}`。礼物名、数量若要从 sidecar 传到模板，这是外部输入的模板问题。

**定时截图讲解**（`image_recognition`，默认关；`main.py` 1575 行起）：截窗口或摄像头，把图交给视觉模型，提示词默认「请讲解一下图片里的内容」。讲解文本若要进主链，形态应和弹幕一样走外部输入，导演只看见讲解句子。视觉客户端不要进 director crate。

### 4.3 和现行产品口径冲突，不借鉴

**助播看的是角色刚说出口的文本。** `audio_synthesis_handle` 在主消息交给播放之后，若 `type` 落在 `assistant_anchor.type` 里，就用这段 `content` 去匹配助播的文本问答库或音频文件名（`my_handle.py` 721–820 行）。默认用户名「助播」，优先级 25，插在普通弹幕前面。

维护者 2026-09-21 的口径是：情绪决策的输入是用户输入，不是角色回复；不要照「分析角色自己说了什么再做表情」改。助播就是这条被否定的路。导演继续不读主模型回复。

**TTS 情绪字符串。** 对方把 `emotion` 写进 Bert-VITS2 / GPT-SoVITS 请求。本仓表演协议写明导演不产 TTS 参数；`suggested_tts` 的 speed/pitch 只出现在状态面板。讨论导演时不要把「顺手把情绪传给 TTS」算进来。

## 6. 讨论时可直接拍板的边界

| 提议 | 建议 |
| --- | --- |
| 给进入主链的外部文本加来源标签，导演规则可以按礼物 / 弹幕选不同预设 | 可以讨论。标签在 `external-input` → `TurnPrompt`，`derive` 仍是纯函数 |
