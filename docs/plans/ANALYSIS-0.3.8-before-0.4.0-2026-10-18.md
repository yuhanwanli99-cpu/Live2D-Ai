# 0.3.8 该不该开：给 0.4.0 做系统性清债的工程侧分析

> **2026-10-18 验收后**：`0.3.6` / `0.3.7` / `0.3.8` 已本地收口。本文「不要为清债开 0.3.8」仍然有效；`0.3.8` 实际做成了 A2A，不并进 `0.4.0`。下文「硬门禁全部通过」在 `code-stats` 上不成立：`live2d_stage.dart` 844 行、`RATCHET_DART_800 = 0`，0.3.8 前后都是这样，本块未改该文件。不要把它当成 0.3.8 引入的债，也不要为它单开版本。
>
> 结论先行：**不值得为「清债」单独开 0.3.8**。当前硬门禁全部通过；清债按既定规则应留在每块最后的
> `rc.(z+1)`。只有在「轻量化 / 首屏」被当成一块**用户可见功能**时，才值得开 0.3.8，且必须有量化
> 退出指标——否则它就会退化成刚被否掉的「单独清债版」。实测数据 2026-10-18，本树。

## 2. 为什么「清债版」不成立

1. **违反版本规则**：`0.x.y-rc.z` 的清理就是最后 `rc.(z+1)`，且规则明确「清理不另开一个版本号」。
   0.3.8 若只做工程债 / 文档 / 代码精简，就是被否掉的「单独清债版」。
2. **ROI 为负**：一个块要一队 agent、一次提交、一个附注 tag、一篇发布说明和文档行数；换来的是
   「门禁仍然 PASS」而不是用户可见变化。项目历史（0.2.0 去臃肿轮、W2/D1 物理删除）也说明大扫除
   需要独立审计，不是顺手能清的。
3. **真正的 0.4.0 风险不在代码洁癖**：Windows 支持要先回答「在哪编译、在哪验证」。当前纪律是
   WSL2 唯一构建/进程宿主，Windows 只做浏览器肉眼；**不 push** 意味着 GitHub Actions 的
   windows runner 也用不上。清债块不会变出 Windows 工具链。
4. **0.4.0 的边界应保持纯净**：它只做 Windows。把全局重构塞进去会让「平台移植失败」和
   「重构回归」混在一起，bisect 困难；反过来，先做一个无用户交付的清债块，也不能降低移植本身的
   未知数。

## 3. 什么情况下才开 0.3.8

只有满足**至少两条**，且它被定义成一块**功能**（不是「清理」）才开：

- 离线包 / 首屏被当成产品指标：目标 Flutter ≤35 MiB（现已 29.32）或 wasm ≤4.2 MiB（需先解决
  `wasm-opt` 缺失，否则是未验）；首屏加载时间有基线、有前后对比。
- docs 逼近 44,000 行，0.4.0 的 Windows 文档放不下；需要先真删/移出（按 DOC-MAP 的移出规则）。
- `>500` 文件数超过棘轮上限或维护者要求降到 15；或依赖数要降回 22 才能给 0.4.0 腾位置。
- 明确要删已退休对象（例如 workspace 里仅剩兼容层的 director crate），且维护者已裁决。

若开，退出指标必须可测：docs ≤40,000、`>500` ≤20、依赖 ≤23、Flutter ≤35 MiB、wasm ≤4.2 MiB
（或明确继续接受并写「未验」）、零新增依赖；最后仍用 `rc.(z+1)` 清这一块。达不到就别开。

## 4. 建议顺序

1. **0.3.6**（热换 P0 / cue / 设置纪律）→ **0.3.7**（LLM 云本地 / 动作）——两块末步各自清债。
2. **0.4.0** 第一件事不是写代码，是定 Windows 构建 + 验证通道（本机 Windows Rust，或维护者
   允许的 CI 路径）；`rc.1` 内做一次**有界的门禁维护**（为 Windows 文档腾 docs 余量、审计依赖、
   确认 ratchet 不退），这属于「为这一块腾空间」，不是另开清债版。
3. 如果之后确实要把「轻量化」做成卖点，再开 `0.3.8`（或直接 `0.4.2`）作为**功能块**，用
   `3` 的指标验收。

**一句话**：0.3.8 作为「系统性清债」不必要；作为「轻量化功能」才有存在理由。当前最该先解决的是
0.4.0 的 Windows 验证路径，而不是代码行数。
