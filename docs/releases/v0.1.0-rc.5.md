## 3. 语义钉死（避免下一轮再解释一遍）

- **一份真相**：`syncShellStageBg == true`（默认）时，壳画的就是 `stageImage`；
  此时「壳背景」那一行的选图 / 清图**改的也是 `stageImage`**。于是不存在
  「舞台换了、壳还是旧的」——只有同步**关掉**才会写壳自己的 `shellImage`。
- **管道不同**：舞台图走渲染面协议 `stage-bg`（iframe 里的 canvas 画）；
  壳图是 **Flutter 自己画的**。两者可以共用同一张图，但**不要合并成一条路**。
- **固定透明度**：0.15 是常量，不是用户参数。任务书明确「不要做 opacity 滑条」。
- **不做的事**（任务书「禁止」，本轮逐条遵守）：分区独立背景、轮播、写入
  `live2d-ai.toml`、背景 Mod、在线 URL 拉图、Action / 导演、动态加载。
  背景只住本机 `DisplayPrefs` / `localStorage`。

## 3.1 rc.5 修复一（**已废弃，见 §3.3**）：舞台背景图不显示（`background-image` 长手属性）

> **追加（2026-09-14）：本节整条路线已废弃。** CSS 值修对之后舞台**仍被黑幕盖住**
> （§3.2），而 §3.2 的「WebGL2 优先」在用户机也**未生效**（§3.3）。最终方案是把舞台
> 底色与背景图**画进 framebuffer**。本节保留为排查记录——**不要再基于它改代码**。

**现象**：rc.5 后标题栏（Flutter 壳）能看到背景图，**Live2D 舞台区域仍纯黑**。

**排查结论（逐条对应用户给的假设链）**：

1. Flutter 侧**送达正常**：`_applyPrefs` 与 `Live2DStage._attach` 都在发
   `stage-bg`，`dataUrl` 非空——标题有图 ⇔ `effectiveShellImage == stageImage`
   非空，反证 `stageImage` 有值。
2. 渲染面**收到了**：`main.rs` 的 `stage-bg` 分支写入 `bridge.bg_data_url`，
   `applied_bg` 变化判定也成立。
3. **写进 DOM 的那条 CSS 值是非法的**（真根因）。旧实现写的是：

   ```text
   canvas.style.background-image = url(<dataURL>) center/cover no-repeat
   ```

   `background-image` 是**长手**属性，只接受 `<image>#`（`none | url(...)`）。
   `center` / `cover` / `no-repeat` 属于 `background-position` / `background-size` /
   `background-repeat`。CSS 解析器遇到非法值会**把整条声明丢弃**，而
   `style.setProperty` **不报错**——于是 `canvas.style.backgroundImage` 恒为空串。
   症状因此极具误导性：同一张图在标题栏正常，舞台却一直纯黑。
4. **（初步判断，后被 §3.2 推翻）曾以为「不是被不透明合成盖住」**：当时看到
   `gpu.rs` 写「优先 `PreMultiplied`」、`model_core.rs` 的色附着是
   `LoadOp::Clear(TRANSPARENT)`，就以为 canvas 透明合成成立。**实际不是**：
   `caps.alpha_modes` 里根本没有 `PreMultiplied`，WebGPU 路径的 canvas 必然不透明
   （证据与修法见 §3.2）。所以「纯色底可见」这个前提从未被验证过——黑主题的黑幕与
   黑色纯色底**肉眼同色**。修完本条（CSS 值合法）之后舞台**仍被黑幕盖住**，
   必须继续做 §3.2。

**修复**（`crates/l2d-wasm-demo`）：

- `background-image` 只写 `url(...)` / `none`；位置 / 尺寸 / 重复分写三个长手属性；
- 换算抽成**原生可测**的 `src/stage_css.rs`（`bg_image_css`）——旧实现埋在
  wasm-only 的 `web::surface::input` 里，原生 `cargo test` **编译不到**，
  等于没有回归（与 `mouth.rs` 同一条教训）。

**回归**：`bg_image_css_is_a_valid_background_image_longhand` 断言值只能是单个
`url(...)` token、**不含任何空白**（有空白就说明又缀了别的 token）；
`bg_image_css_keeps_a_real_data_url_intact` 用真实 dataURL 形状再钉一遍。
`cargo test -p l2d-wasm-demo` 原生 **7 passed**（含这 2 条）。

**可复现 / 自检**（Windows 浏览器 F12 Console；同源可直接读 iframe 文档）：

```js
const c = document.querySelector('iframe').contentDocument.querySelector('canvas');
({ image: c.style.backgroundImage.slice(0, 40), size: c.style.backgroundSize,
   position: c.style.backgroundPosition, repeat: c.style.backgroundRepeat })
```

选图后应为 `image` 以 `url(` 开头、`size: 'cover'`、`position: 'center'`、
`repeat: 'no-repeat'`；修复前 `image` 是空串。

**注意**：渲染面产物在 `crates/l2d-wasm-demo/dist`（被 `.gitignore` 的 `dist/` 排除），
改 wasm 后必须 `cd crates/l2d-wasm-demo && unset NO_COLOR && trunk build` 重建，
否则改的是源码、跑的还是旧 wasm。

## 3.2 rc.5 修复二（**已证伪并回滚，见 §3.3**）：黑幕盖住舞台（WebGPU 的 canvas 必然不透明）

> **追加（2026-09-14）：本节的「WebGL2 优先」在用户机未生效。**
> `/render?hud=1` 实测 `GPU: webgpu/WebGPU`——`request_gl` 失败后回退到了 WebGPU。
> 该改动已**回滚**（`gpu.rs` 恢复 WebGPU 优先），并认定「靠 canvas 透明露 CSS 背景」
> 这条路由**结构性不可达**。本节的 wgpu 证据仍然有效，且正是 §3.3 的依据。

**现象**（§3.1 修复后、CSS 值已合法）：加载瞬间舞台能闪到背景，随后被**黑幕铺满**；
DevTools 里 `canvas.style.backgroundImage` 已是合法 `url(...)` 也没用。

**根因**（证据在 wgpu 29.0.4 源码里，不是猜）：

- `webgpu` 后端的 `get_capabilities` 只返回 `alpha_modes: vec![Opaque]`
  （`wgpu-29.0.4/src/backend/webgpu.rs`）；
- `wgpu-core` 对 caps 之外的 `alpha_mode` 直接以 `UnsupportedAlphaMode` **拒绝**
  （`wgpu-core-29.0.4/src/device/resource.rs` 的 surface configure 校验）；
- 所以 WebGPU 路径**无法请求 `PreMultiplied`**，canvas 必然以
  `GpuCanvasAlphaMode::Opaque` 合成 → `LoadOp::Clear(TRANSPARENT)` 的像素被合成
  成**不透明黑**，整块 canvas 变成黑幕，盖住它自己的 CSS 背景；
- 为什么以前「看起来没事」：黑主题的舞台色就是 `#000000`，黑幕与纯色底**肉眼同色**，
  于是「`background-color` 生效」这个假设从未被真正验证过；
- WebGL2 路径相反：`wgpu-hal` 的 `gles/web.rs` `create_context_options` 只设
  `antialias=false`，WebGL 上下文 `alpha` **默认 true**，透明合成成立。

**修复**：`gpu.rs` 改为 **WebGL2 优先、WebGPU 回退**（一行级取舍；回滚只需调换两个
`request_*` 的顺序）。canvas 因此保持透明 framebuffer，§3.1 已修好的 CSS
`background-color` + `background-image` 能稳定露在角色周围空白处；叠放语义不变
（图盖在纯色底上，清除图回纯色）。

**代价（显式记录，不是疏忽）**：WebGL2 性能一般低于 WebGPU。这是为「舞台背景可见」
付的显式代价。恢复 WebGPU 的正解是把舞台背景**画进 framebuffer**（clear 用
stageColor + 全屏三角贴图），那要 `l2d` 让出 `LoadOp::Load` 并新增一条背景管线——
列为后续项，不在本轮。

**回归**：`render_backend_policy_tests::web_renderer_prefers_webgl2_then_falls_back_to_webgpu`
（原生 `cargo test` 可跑）用 `include_str!` 扫描 `gpu.rs`：断言 `request_gl` 出现在
`request_webgpu` 之前，且**不再**出现 `Backends::BROWSER_WEBGPU | wgpu::Backends::GL`
的旧写法。

**验证**：切到**白主题**——修复前舞台仍是黑的（黑幕盖着），修复后应为白色纯色底；
选图后图应稳定显示在角色周围，刷新与切主题都不掉。

## 3.3 rc.5 修复三（**最终方案**）：舞台背景画进 framebuffer

**验收目标**（用户口径）：白主题舞台为白；选图后角色周围**稳定**有图、不再
「闪一下后全黑」；清图回纯色。

**做法**（不再依赖任何 CSS、不再动后端顺序）：

1. **背景预通道**（`l2d-wasm-demo/src/web/surface/background.rs`）：
   `LoadOp::Clear(<当前 stageColor>)` → 有背景图时再画一个**全屏三角形**、按
   `cover` 采样背景纹理；
2. **模型通道**（`l2d`）：改用新增的
   `render_to_view_submit_with_load(view, format, LoadOp::Load)`——只叠 Live2D，
   **不再 clear**（否则预通道铺的底色与图会被擦掉）；
3. 叠放语义不变：**图盖在纯色底上、模型在最上层、清图回纯色**；
4. 于是结果与「canvas 是否透明」**完全无关**，WebGPU 保持默认（HUD 仍报真实 backend）。

**异步解码**：`stage-bg` 的 dataURL 经 base64 解码 → `Blob` →
`createImageBitmap` → `OffscreenCanvas` 2D → `ImageData` → `queue.write_texture`。
用浏览器解码器意味着 PNG/JPEG/WebP 全支持，且**不引入任何 Rust 图像依赖**；
坏图 / 非图片 → 退回纯色底（不留上一张）。解码期间先保持纯色底，装好后自动切图。

**可测性**：纯逻辑抽到原生可跑的 `l2d-wasm-demo/src/stage_bg.rs`——
`base64_decode_data_url`、`cover_uv`（`background-size: cover` 的 UV 变换）、
`clear_color`（含非法值回落到 `dark`/`light` 默认色的判定）。
GPU 部分（管线/纹理）只能在浏览器验，但**所有算术**都有原生回归。

**HUD**：新增 `bg: solid|image` 字段（`/render?hud=1`）——选图解码完成后应变成
`bg: image`，是「图到底有没有上屏」的直接信号。

**已废弃**：canvas 的 CSS `background-color` / `background-image` 写入**已删除**
（`stage_css.rs` 随之删除）——canvas 不透明时它们永远看不见，留着只会误导。
纯色底的可见来源现在是 **framebuffer 的 clear 值**。
