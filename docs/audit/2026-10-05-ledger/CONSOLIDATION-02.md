## ④ 跨批系统模式（本轮对账最有价值的产出）

### 模式 B 的三种写法 —— **本轮修订了上一次的对账结论**
上次我写的是「假绿灯有三种固定写法，频率异常高」。**本轮 49 个 web_api 文件复查后，这个结论需要收窄**：

| 写法 | 命中处 | 说明 |
|---|---|---|
| ① 析取式断言恒真（`assert!(A \|\| !B)`，而 B 在目标环境恒成立） | `model_root.rs:111` | 1 处 |
| ② 测试名/头注承诺的契约没进测试体 | `supervisor_slot.rs:172-204` | 1 处 |
| ③ **round-trip 测试起点为空**（名字承诺「不丢 X」，但起点没有 X 之外的任何东西） | `mod_registry.rs:944-966`、F-0013-02 | 1 处 |
| ④ **新增变体没进「稳定性测试」**（`RouteId::Env` 不在 `route_id_as_str_is_stable` 里） | `tests_mod.rs:153-167` | 1 处 |

⇒ **四次命中，四种写法，但总共只有 4 处，分布在 4 个文件里**，而这两个目录共读了约 75 条测试。
**结论修订：假绿灯不是本仓的系统性文化问题，而是「写新测试时容易犯的四种具体错误」**。
正面证据同样强：`tests_dev_mode.rs` 9 条零问题且是质量上界；`tests_ws.rs` 28 条零问题；
`audio_tests.rs` 把「一句恰好一个 start 一个 end」逐帧钉死；`chat_routes.rs:531-534` 主动写注释
解释「为什么断言引用常量而不是钉死数字」——**团队具备写出高质量测试的能力，只是没每处都这么写**。

### 模式 E（新，本轮最强）：**panic / 失败沿调用栈向上扩散，而缺少拦截层**
三处独立发现指向同一个结构：
- `mod_registry.rs:334/434/617` 的 `.lock().unwrap()` → panic 出 `run_request_loop` 的裸 `for`（无 `catch_unwind`）→ **整个 HTTP 服务停摆**（F-0006-03，P1）
- `models_routes/mod.rs:167-179` 的 registry 损坏告警只走 `eprintln!` → 不进日志 sink（F-0008-02，P3）
- `chat_routes` / `external_routes` / `voice_routes` / `mods_routes` 四个模块 `tracing::` 全为 0（F-0001-01，P1）

**共同点：请求处理路径上没有任何一层「兜底 + 记账」**。panic 会打穿服务，
失败不会留痕。这与仓库自己在 AGENTS.md 里立的红线（「链路错误必须同时进 tracing 与前端 WS 帧」）
方向完全相反——那条纪律被用在了**主链路**（LLM/TTS/WS 帧）上，却**没有**用在外围 HTTP 端点与 Mod 装配面上。
**判据**：任何 `fn(req) -> Response` 到 `run_request_loop` 之间，若路径上没有
「panic 拦截」与「分级日志」两道，缺陷就会从「一个端点出错」升级为「服务消失 / 排障时一片空白」。

### 模式 D（累计 7 例，修订）：护栏注释与实际装配脱节
