## ④ 跨批系统模式

### 模式 E 复核与扩充：**失败沿调用栈向上扩散，且路径上缺少拦截层与记账层**
上轮记的是 web_api 侧 3 处。runtime 侧**新增 2 处**，且形态更极端：

| # | 位置 | 形态 |
|---|---|---|
| 1 | `mod_registry.rs:334/434/617` `.lock().unwrap()` | panic 逃出 `run_request_loop` 裸 `for`（无 `catch_unwind`）→ **整个 HTTP 服务停摆**（F-0006-03，P1） |
| 2 | `models_routes/mod.rs:167-179` registry 损坏告警 | 只 `eprintln!`，不进文件 sink → 唯一会清空用户模型列表的事件**日志无痕**（F-0008-02，P3） |
| 3 | `conversation/{worker,engine}.rs` `tracing::` 计数 | **均为 0**；`worker.await.unwrap_or(WorkerExit::Failed)` 把 panic 消息整个丢弃 → 用户看到「说了半句就没了」，**日志一字无**（F-0015-01，P2） |
| 4 | `performance/mod.rs:352-362` + `:370` | `fallbacks` 双计 → 唯一的性能健康指标**算错**（F-0019-01，P2） |
| 5 | `app_routes.rs:292-295` `PerformanceStatus.has_api_key` | 手搓判据、漏走同仓已有的 `key_is_ready` → 状态面与设置面**同屏不同义**（F-0002-03，P2；本轮由 B0021 补上参照实现精确化） |

**判据（不变，但现在有 5 个样本）**：
从「一次失败」到「用户能看见发生了什么」之间，本仓缺两道工序：
**(a) 拦截层**——请求/任务处理路径上没有 `catch_unwind`，panic 直接打穿服务；
**(b) 记账层**——失败要么只进 HTTP 响应体、要么只进 `eprintln!`、要么被 `unwrap_or` 吞掉。
值得注意的是：**(b) 在 web_api 与 conversation 两个最核心的路径上命中 4/5**，
而项目自己在 AGENTS.md 立的红线（「链路错误必须同时进后端 tracing 与前端 WS 帧」）
**只用在了主链路的 LLM/TTS 错误上**，外围 HTTP 端点、Mod 装配面、TTS worker、
性能层计数全部没继承那条纪律。

### 模式 F 复核与扩充：**持久化/度量用「重建」而非「合并」**
上轮 2 例（`persist_manifest` 丢未知 id、`model_registry` 的 `deny_unknown_fields`）。
本轮在**非持久化**的度量面也出现同形：

| # | 位置 | 形态 |
|---|---|---|
| 1 | `mod_registry.rs:253` `persist_manifest` | 从内存注册表**重建**整份 `mods.json`，未知 id 永久消失（F-0013-01，P1） |
| 2 | `models_routes/registry.rs` 6 处 `deny_unknown_fields` | 读侧遇未知字段即判「损坏」→ 清空（F-0007-01，P2） |
| 3 | `performance/mod.rs:353` + `:370` | `fallbacks` 计数在**两个**地方各 +1，没有单一写入点（F-0019-01，P2） |

**判据（扩充）**：凡是「从一份**已知的全集**重新生成目标」的地方——
无论是写文件、还是算计数——都要问一句「我**不**知道的那部分去哪了」。
已知全集是够的（3/3 都是「我掌握的部分」驱动），而每处都漏了。

### 模式 G（新，本轮最强）：**「可观察面」被三处各自独立地兑现又独立地断掉**
本轮最有价值的产出。它跨越三个 crate、三种技术：
1. **服务端造好了**：`view.rs` 的 `SettingsView.performance`（注释「面板据此显示现状」）、
   `dto.rs` 的 `AppStatus.performance`（注释「这是『表演层到底有没有在工作』的可观察面」）、
   `plan.rs` 的 `warnings` 逐条带 code、`error_code.rs` 的 `hint()` 全变体覆盖无兜底。
2. **前端没接**：`grep -rni performance shell/flutter/lib/` 14 处命中**全是** `performance.now()`
   与中文注释；诊断面板读 `app/status` 的 7 个键里**不含** `performance`；
   设置面板改用**硬编码文案**「配置只在 live2d-ai.toml 的 [performance] 段」。
3. **于是**：`performance` 这个特性在产品里既**不能配置**（面板不给入口）、
   也**不能观察**（指标不下发到界面）、**出问题也不知道**（回退静默）。

**判据**：当一条「可观察面」的文档承诺了消费者（「面板据此显示现状」/「这是…可观察面」），
而**消费者侧零引用**时，注释就成了**反向承诺**——它让维护者相信这条链路是通的。
本轮 7 条发现里有 2 条（F-0021-01、F-0020-01）直接由这条模式派生，
而它们的**根**都在服务端，**症状**都在客户端。这是「跨端契约审计」的典型产出：
单看任一侧都自洽，合起来才看得见。
